Tipos de Arquitectura de Software

Investigación y Aplicación al Proyecto "BioScan Cochabamba"

1. ¿Qué es la Arquitectura de Software?

La Arquitectura de Software es el diseño de más alto nivel de un sistema informático. Es como el "plano de una casa", pero para un programa. Define cómo se organizan los componentes del software, cómo se comunican entre sí y las decisiones fundamentales sobre las tecnologías que se usarán para cumplir con los requisitos del proyecto (rendimiento, seguridad, escalabilidad, etc.).

2. Explicación de los Tipos de Arquitectura

A. Arquitectura Monolítica

Todo el sistema (interfaz de usuario, lógica de negocio y acceso a datos) se desarrolla, empaqueta y despliega como una única aplicación indivisible.

✅ Ventajas ❌ Desventajas
- Fácil de desarrollar, probar y desplegar al inicio.
- Ideal para equipos pequeños o proyectos sencillos.		 - Difícil de escalar y mantener cuando el código crece mucho.
- Si una parte falla, se cae todo el sistema.

Ejemplo: Un blog básico en WordPress o un sistema de inventario sencillo de una pequeña farmacia donde todo corre en un solo archivo ejecutable.

B. Arquitectura en Capas (N-Tier)

Divide el sistema en niveles horizontales (generalmente: Presentación, Lógica de Negocio y Datos). Cada capa solo se comunica con la capa inmediatamente inferior.

✅ Ventajas ❌ Desventajas
- Muy ordenada y estandarizada.
- Separación de responsabilidades: los cambios en una capa (ej. diseño visual) no afectan a las demás (ej. base de datos).		 - Puede generar código innecesario o redundante si la aplicación es muy simple (la información debe atravesar todas las capas obligatoriamente).

Ejemplo: La mayoría de aplicaciones empresariales tradicionales en lenguajes como Java (Spring) o Node.js (NestJS), donde hay controladores web, servicios de negocio y repositorios de base de datos.

C. Arquitectura Cliente-Servidor

Separa claramente la interfaz del usuario (Cliente) del procesamiento y almacenamiento de datos (Servidor). El Cliente hace peticiones y el Servidor responde.

✅ Ventajas ❌ Desventajas
- Centralización de datos y seguridad (el servidor protege la información crucial).
- Permite tener múltiples clientes (Web, Móvil, Escritorio) conectados al mismo servidor.		 - Si el servidor se cae, ningún cliente puede funcionar.
- Requiere una conexión a red estable para funcionar correctamente.

Ejemplo: Plataformas como Spotify o Netflix. Tú tienes la app en tu celular (Cliente), pero las canciones, películas y tu cuenta viven en sus centros de datos (Servidor).

D. Arquitectura de Microservicios

El sistema se divide en servicios muy pequeños e independientes que se comunican entre sí (generalmente por red). Cada servicio hace una sola cosa muy bien y tiene su propia base de datos.

✅ Ventajas ❌ Desventajas
- Altamente escalable: puedes darle más potencia solo a la parte que lo necesita.
- Si un servicio falla (ej. sistema de comentarios), el resto de la app sigue funcionando.		 - Extremadamente compleja de configurar, monitorear y mantener.
- Sobrecarga en la red por mucha comunicación entre microservicios.

Ejemplo: Aplicaciones gigantes como Uber (un microservicio calcula la ruta, otro cobra la tarjeta, otro asigna el conductor) o Amazon.

3. ¿Qué Arquitectura aplicamos en BioScan Cochabamba?

Para nuestro proyecto BioScan Cochabamba, utilizamos una combinación de Arquitectura Cliente-Servidor a nivel general, y Arquitectura en Capas a nivel del backend.

1️⃣ Arquitectura Cliente-Servidor (A nivel macro)

Nuestro proyecto está dividido físicamente y lógicamente en dos partes que se comunican a través de internet (API REST):

  • El Cliente (Frontend Web): Desarrollado en HTML, CSS y JS (o frameworks modernos). Se encarga de mostrar el mapa interactivo (Leaflet), capturar las fotos desde el navegador del usuario y presentar los resultados.
  • El Servidor (Backend en NestJS): El "cerebro". Recibe la foto, procesa la petición y se conecta a las Inteligencias Artificiales (Plant.id, Groq, iNaturalist).

¿Por qué elegimos Cliente-Servidor?

  • Seguridad Crítica: Para usar la IA necesitamos "API Keys" (claves secretas). Si pusiéramos todo junto en el frontend (Monolítico simple), cualquier usuario podría robar nuestras claves. Al tener un Servidor, las claves están ocultas y protegidas; el usuario solo interactúa con el frontend que le pide al servidor los datos.
  • Escalabilidad futura: Si el día de mañana la Alcaldía decide que quiere una App Nativa móvil (Android/iOS) para los guardaparques del Cerro San Pedro, solo necesitamos crear el nuevo Cliente móvil. No hay que reescribir el Servidor, porque ya está separado.

2️⃣ Arquitectura en Capas (Dentro del Servidor NestJS)

Al programar el backend con el framework NestJS, estamos aplicando inherentemente una arquitectura de capas estructurada:

  • Capa de Presentación / Controladores (Controllers): Son las rutas de nuestra API (ej. /api/identificar). Solo reciben la foto, validan que el archivo sea correcto y se lo pasan a la siguiente capa.
  • Capa de Lógica de Negocio (Services): Aquí ocurre la magia. El servicio toma la foto, la procesa, la envía a la IA de reconocimiento visual, extrae la probabilidad y formula la respuesta final estructurada.
  • Capa de Datos (Repositories/Data): Se encarga de leer el registro histórico de especies (en un archivo JSON o base de datos) del Cerro San Pedro.

¿Por qué elegimos Arquitectura en Capas internamente?

  • Trabajo en equipo limpio: Al estar el código tan ordenado, diferentes personas del equipo pueden trabajar en la lógica del Chatbot y en la de Identificación Visual al mismo tiempo sin causar conflictos en el código.
  • Mantenibilidad: Si mañana decidimos cambiar la IA de "Plant.id" por "Azure Custom Vision", solo modificamos la Capa de Lógica. El Controlador (la ruta web) no sufre ningún cambio, lo que evita que el sistema se rompa inesperadamente.

Resumen para el informe: Descartamos el modelo Monolítico por falta de seguridad para nuestras APIs de IA, y descartamos Microservicios porque aportaría una complejidad innecesaria a un MVP (Producto Mínimo Viable). La combinación de Cliente-Servidor + Arquitectura en Capas (con NestJS) nos brinda el equilibrio perfecto entre seguridad, rapidez de desarrollo, orden técnico y profesionalismo para la hackathon y para un entorno real de negocio.
